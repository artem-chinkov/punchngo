# 1. Цель разработки

Разработать полностью играбельный прототип мобильного браузерного файтинга от первого лица.

Прототип должен воспроизводить основные механики, утверждённые в Game Design Document v1.0.

Ключевая техническая задача — реализация псевдотрёхмерного мира с движущейся извилистой дорожкой, масштабируемыми объектами окружения и противниками, которые могут перемещаться и сражаться перед камерой.

## Основные требования

- Только вертикальная ориентация смартфона.
- Phaser 4 + TypeScript + Vite.
- WebGL как основной способ рендеринга.
- Детализированный пиксель-арт.
- Псевдо-3D без полноценного 3D-движка.
- Автоматическое движение по дорожке.
- Остановка на время боевых столкновений.
- Полноценная боевая система из GDD.
- Один завершённый уровень.
- Внутреннее меню разработчика.
- Локальное тестирование перед публикацией на GitHub Pages.

Первая задача — получить корректно работающий игровой прототип. Временные ассеты допустимы до готовности оригинальной графики.

# 2. Архитектура приложения

## 2.1. Принцип разделения

Игровое приложение должно состоять из трёх независимых логических уровней.

### Game Simulation

Отвечает за игровое состояние:

- Координаты и расстояния.
- Продвижение героя.
- Состояния противников.
- Боевые столкновения.
- Урон и здоровье.
- Выносливость.
- Комбо.
- Очки.
- Контрольные точки.
- Условия победы и поражения.

Вычисления должны работать независимо от визуальных изображений и анимаций.

### Rendering

Отвечает исключительно за отображение:

- Дорожки и поворотов.
- Дальнего фона.
- Объектов окружения.
- Врагов.
- Кулаков героя.
- Эффектов.
- HUD.

Рендеринг получает актуальное игровое состояние и преобразует его в изображение.

### Input

Обрабатывает касания, различает короткие тапы и удержание пальца, передаёт действия в боевую систему.

Input не должен напрямую изменять здоровье противников или счёт.

## 2.2. Игровые сцены Phaser

Предлагаемая структура:

**BootScene**

Инициализация игры, проверка конфигурации, переход к загрузке.

**PreloadScene**

Загрузка изображений, атласов, аудио и конфигураций.

**MenuScene**

Стартовый экран, кнопка начала игры, отображение лучшего результата.

**GameScene**

Основная сцена, управляющая игровым миром, боем и рендерингом.

**UIScene**

HUD и контекстные сообщения поверх игрового мира.

**ResultScene**

Экраны поражения и завершения уровня.

**DebugScene**

Внутреннее меню балансировки, графические зоны и диагностические данные.

Для обмена информацией между сценами использовать централизованное состояние и типизированные события. Не создавать несколько независимых источников истины для здоровья, очков или прогресса.

# 3. Псевдо-3D — основная технология

## 3.1. Выбранный подход

Использовать сегментную перспективную проекцию, аналогичную подходам классических аркадных гонок.

Не использовать Three.js или полноценный трёхмерный физический движок.

Дорожка представляет собой последовательность сегментов, имеющих параметры:

- Начальная и конечная дистанция.
- Ширина.
- Кривизна.
- Визуальные свойства покрытия.
- Привязанные объекты окружения.

Игровые объекты существуют в условной системе координат мира и проецируются на экран.

## 3.2. Координаты мира

Использовать единую систему:

**Z** — расстояние вдоль маршрута.

**X** — горизонтальное смещение относительно центра дорожки.

**Y** — высота объекта над землёй, если она необходима для визуального эффекта.

Позиция героя определяется пройденным расстоянием по маршруту.

Враг имеет собственную координату Z, а также боковое смещение X.

Для объектов окружения использовать тот же принцип.

Так можно рассчитывать расстояния и дистанцию атаки без 3D-физики.

## 3.3. Проекция объектов

Экранный размер объекта определяется расстоянием до виртуальной камеры.

Близкий объект отображается крупным, дальний — маленьким.

Проекция должна рассчитывать:

- Экранную позицию по горизонтали.
- Экранную позицию основания объекта.
- Масштаб.
- Видимость.
- Порядок отрисовки.

Для противников точкой привязки должны быть ступни, а не центр изображения.

Объекты, находящиеся за камерой или вне допустимой дистанции отрисовки, скрываются.

Масштаб ограничивается безопасными пределами, чтобы избежать деления на слишком малую дистанцию и чрезмерного увеличения изображения.

## 3.4. Геометрия дорожки

Каждый видимый участок дорожки рисуется как трапеция.

Проецируются ближняя и дальняя границы сегмента. Между ними строится четырёхугольник.

Сегменты отрисовываются от дальнего к ближнему.

Покрытие дорожки включает:

- Основной цвет.
- Боковые границы.
- Небольшие изменения оттенка.
- Декоративные детали покрытия.

В первой версии геометрию можно рисовать через Phaser Graphics.

Необходимо избегать создания большого количества новых графических объектов в каждом кадре.

## 3.5. Плавные повороты

Для каждого участка хранится значение кривизны.

Поворот не требует вращения полноценной 3D-камеры.

Вместо этого последовательные сегменты дорожки постепенно смещаются относительно виртуального центра изображения.

Кривизна изменяется плавно:

- Вход в поворот.
- Основной участок поворота.
- Выход из поворота.

Направления поворотов: влево и вправо.

Важное требование: деревья, лавки, фонари и противники должны использовать ту же модель изгиба, что и дорожка.

Нельзя рассчитывать перспективу дорожки и боковых объектов независимо, иначе объекты визуально будут съезжать со своих мест на поворотах.

## 3.6. Дальний фон

Дальний фон состоит из нескольких слоёв:

1. Небо.
2. Удалённые городские здания.
3. Дальний лес или деревья.
4. Ближняя растительность у линии горизонта.

Каждый слой может смещаться по горизонтали с небольшой разной скоростью для создания параллакса.

Фон не должен масштабироваться по тем же правилам, что деревья у дорожки.

## 3.7. Движение по маршруту

Во время состояния MOVING:

- Позиция героя по Z увеличивается.
- Сегменты дорожки проходят под виртуальной камерой.
- Объекты приближаются.
- Камера следует плавным изгибам маршрута.
- Шкала прогресса уровня обновляется.

Во время состояния COMBAT:

- Продвижение героя по маршруту останавливается.
- Дорожка и статичное окружение остаются на месте.
- Противники могут продолжать собственное движение относительно героя.
- Камера может незначительно реагировать на удар, блок и выбранную цель.

Рекомендуется считать движение по маршруту и движение врагов отдельными процессами.

## 3.8. Детали дорожки

Для повышения качества пиксель-арта использовать отдельные детали:

- Трещины.
- Листья.
- Мелкие камни.
- Пятна и изменения покрытия.

Каждая деталь должна иметь координаты мира и масштабироваться в перспективе.

Не размещать детали случайно каждый кадр.

Для первого уровня использовать фиксированные декоративные элементы, чтобы изображение оставалось стабильным при повторных прохождениях.

# 4. Система окружения

## 4.1. Типы объектов

Предусмотреть:

- Деревья нескольких размеров.
- Кусты.
- Парковые лавочки.
- Фонари.
- Мелкие декоративные объекты.

Все элементы должны поддерживать перспективное масштабирование.

## 4.2. Размещение

Декоративные объекты привязаны к координатам маршрута.

Для каждого объекта хранятся:

- Тип ассета.
- Положение вдоль маршрута.
- Боковое смещение.
- Базовый размер.
- Точка опоры.
- Дополнительные визуальные параметры.

Объекты не должны пересекать основную боевую область так, чтобы закрывать атакующих противников.

## 4.3. Порядок отображения

Объекты игрового мира сортируются по глубине.

Дальние объекты находятся позади ближних.

Необходимо учитывать взаимное перекрытие деревьев, противников и элементов окружения.

Кулаки героя и HUD располагаются поверх всех объектов игрового мира.

# 5. Состояния игрового процесса

Использовать явную систему состояний.

| Состояние | Назначение |
|---|---|
| MENU | Главное меню |
| MOVING | Автоматическое движение |
| ENCOUNTER | Появление и приближение противников |
| COMBAT | Активная схватка |
| CHECKPOINT | Достижение контрольной точки |
| BOSS_INTRO | Появление мини-босса |
| BOSS_COMBAT | Битва с мини-боссом |
| FINISHER | Кинематографичное добивание |
| VICTORY | Завершение уровня |
| DEFEAT | Поражение |
| PAUSED | Пауза |

Переходы между состояниями должны быть контролируемыми.

Пример:

MOVING → ENCOUNTER → COMBAT → MOVING.

При нулевом здоровье:

COMBAT → DEFEAT → CHECKPOINT → MOVING или BOSS_COMBAT.

В состоянии FINISHER обычное боевое управление отключено.

# 6. Управление касаниями

## 6.1. Input Controller

Разработать единый контроллер для распознавания:

- Начала касания.
- Продолжительности касания.
- Отпускания.
- Отмены касания.
- Состояния удержания.

Предварительный порог блока: 180 мс.

## 6.2. Короткий тап

Короткое касание с отпусканием до порога запускает один удар.

Для сохранения отзывчивости сразу при касании может начинаться небольшая подготовительная анимация.

Фактическая атака выполняется при распознавании короткого тапа.

Не допускать дополнительного удара при отпускании после блока.

## 6.3. Удержание

После достижения порога удержания включается блок.

Блок продолжается до отпускания пальца либо до принудительного прерывания состояния.

После завершения блока герой возвращается в боевую стойку.

## 6.4. Обработка ошибок ввода

Обязательно обработать:

- Быстро повторяющиеся касания.
- Несколько одновременных пальцев.
- Прерывание касания.
- Потерю фокуса браузера.
- Переход на другую вкладку.
- Открытие меню.
- Поворот устройства.

Для первой версии дополнительные пальцы можно игнорировать, пока активно первое касание.

На игровом Canvas отключить стандартные браузерные жесты, мешающие управлению.

# 7. Combat System

## 7.1. Независимая логика боя

Боевая система не должна определять попадания по реальным пикселям изображений.

Для каждого противника предусмотрена логическая зона поражения.

Условия успешной атаки:

- Игрок находится в состоянии, допускающем удар.
- Хватает выносливости.
- Цель жива.
- Цель находится на допустимой дистанции.
- Цель находится в секторе атаки.
- Атака не заблокирована игровым состоянием.

## 7.2. Типы ударов

Реализовать:

- Обычный левый.
- Обычный правый.
- Усиленный третий удар.
- Контратака.
- Усиленный удар по оглушённому врагу.

Для каждого типа хранить:

- Базовый урон.
- Стоимость выносливости.
- Дистанцию.
- Сектор поражения.
- Время действия.
- Длительность восстановления.
- Тип реакции цели.

## 7.3. Трёхударная комбинация

Логика короткой комбинации должна отслеживать номер следующего удара.

После первого и второго успешных попаданий последовательность продвигается.

Третье успешное попадание выполняет усиленную атаку.

После третьего удара последовательность начинается заново.

Промах или блок сбрасывают короткую комбинацию.

Чередование левой и правой руки должно сохраняться независимо от номера удара.

## 7.4. Усиленный удар по группе

Основная цель получает 150% базового урона.

До двух дополнительных противников внутри сектора получают 25% базового урона.

Соседи ненадолго отшатываются.

Попадания по соседям не добавляют отдельные единицы длинного комбо.

## 7.5. Контратака

При попадании по противнику в активном окне контратаки:

- Прерывается его текущая атака.
- Активируется оглушение.
- Начисляются очки.
- Восстанавливается часть выносливости.
- Следующий успешный удар по тому же врагу получает бонус.

Текущее предложение по взаимодействию бонусов: сначала рассчитывать урон выбранного удара, затем применять множитель контратаки.

Величину суммарного усиления необходимо проверить при балансировке, особенно для третьего удара.

## 7.6. Защита от ложных промахов

После принудительного отбрасывания врага действует короткое защитное окно.

Если игрок ударил в этот период и не попал:

- Выносливость расходуется.
- Короткая комбинация сбрасывается.
- Длинное комбо сохраняется.

Окно не должно действовать при обычном раннем ударе по ещё не подошедшему противнику.

# 8. Enemy AI

## 8.1. Состояния врага

Использовать конечный автомат состояний:

- APPROACH — приближение.
- POSITIONING — занятие боевой позиции.
- IDLE — ожидание.
- TELEGRAPH — подготовка атаки.
- ATTACK — удар.
- RECOVERY — восстановление после удара.
- HIT_REACTION — реакция на попадание.
- STUNNED — оглушение.
- RETREAT — отступление.
- DEFEATED — поражение.

## 8.2. Боевое позиционирование

Условное пространство перед героем разделено на три зоны.

Противники могут перемещаться между ними.

Каждый враг имеет желаемое боковое положение, которое достигается плавным движением.

Нельзя мгновенно телепортировать противников между позициями.

Избегать чрезмерного перекрытия врагов и полного скрытия одного персонажа за другим.

## 8.3. Очередность атак

Разработать контроллер очередности атак группы.

В один момент только один обычный враг может иметь право на активную результативную атаку.

Остальные продолжают двигаться и ждать подходящего момента.

После удара, его прерывания или поражения атакующего право передаётся другому противнику.

Контроллер должен учитывать тип врага, дистанцию и период восстановления.

## 8.4. Автонаведение

Приоритет:

1. Доступный противник в активном окне контратаки.
2. Текущая цель.
3. Ближайший доступный противник.

Условия:

- Приоритет контратаки применяется только к противнику в зоне досягаемости.
- Обычная цель не должна меняться каждую игровую итерацию.
- После поражения цели выбирается следующая.
- Небольшое боковое движение врага не должно автоматически сбрасывать захват цели.

# 9. Player State

Состояние игрока должно включать:

- Текущее здоровье.
- Максимальное здоровье.
- Текущую выносливость.
- Максимальную выносливость.
- Дистанцию вдоль маршрута.
- Состояние перемещения.
- Состояние текущей атаки или блока.
- Активную руку.
- Номер удара в короткой комбинации.
- Счётчик длинного комбо.
- Идентификатор выбранной цели.
- Активные бонусы.
- Текущую контрольную точку.

Все значения должны обновляться централизованно.

Критически важно отделять логическое состояние игрока от анимации его кулаков.

# 10. Уровень и контрольные точки

## 10.1. Level Configuration

Первый уровень описать как данные.

Конфигурация должна содержать:

- Длину маршрута.
- Последовательность поворотов.
- Расположение окружения.
- Координаты десяти столкновений.
- Состав каждой группы.
- Контрольные точки.
- Позицию мини-босса.
- Условия завершения.

Не привязывать состав волн к произвольным таймерам.

Столкновения активируются по дистанции продвижения.

## 10.2. Возрождение

При поражении восстанавливается согласованный снимок игрового состояния.

Сохраняются:

- Последняя достигнутая контрольная точка.
- Набранный счёт с учётом штрафов.
- История уже начисленных наград.
- Информация о завершении обучения.

Противники текущего повторяемого участка возрождаются.

При этом их повторная победа не должна повторно начислять уже полученные очки.

## 10.3. Мини-босс

Перед боссом отдельная контрольная точка.

При первом входе в бой полностью восстановить здоровье и выносливость.

После поражения от босса повторно запускать его с начала, без повторного прохождения третьего участка.

---

# 11. Scoring System

Система очков должна рассчитываться отдельно от анимаций интерфейса.

Для каждого начисления хранить:

- Причину начисления.
- Базовое количество очков.
- Множитель комбо, если он применим.
- Идентификатор врага или события.
- Флаг ранее полученной награды.

Для каждого уникального противника начисление очков за победу допускается только один раз за забег.

Контратаки и другие события также должны иметь защиту от повторного начисления за один и тот же игровой эпизод.

После поражения применяется штраф 20% от текущего счёта.

Ранг S/A/B/C вычисляется только на основании итоговых очков.

Пороговые значения рангов и базовые награды должны храниться в конфигурации балансировки.

# 12. HUD

## 12.1. Слои интерфейса

HUD не участвует в перспективной проекции.

Все его элементы позиционируются относительно видимого игрового экрана.

**Верхняя часть:**

- Портрет здоровья героя.
- Прогресс уровня.
- Текущий счёт.

**Нижняя часть:**

- Выносливость.
- Индикатор трёхударной комбинации.
- Кулаки героя.

**Контекстные элементы:**

- Комбо.
- Контратака.
- Промах.
- Временное здоровье противников.
- Предупреждения об атаках.
- Обучающие сообщения.

## 12.2. Портрет здоровья

Портрет героя меняется в зависимости от диапазона HP.

Предусмотреть несколько состояний:

- Здоров.
- Лёгкие повреждения.
- Средние повреждения.
- Серьёзные повреждения.
- Критическое здоровье.

Смена изображения не должна влиять на игровое состояние.

## 12.3. Комбо

Значение комбо отображается в центральной области, не перекрывающей атаки противников.

При увеличении значения:

- Кратковременное масштабирование.
- Цветовое усиление при больших сериях.
- Дополнительная анимация при достижении порога множителя.

## 12.4. Временные индикаторы HP

Полоска здоровья конкретного врага привязана к его экранной позиции.

При изменении масштаба и положения врага индикатор перемещается вместе с ним.

Через 1,5 секунды после последнего попадания скрывается.

# 13. Интеграция графических ассетов

## 13.1. Форматы

Основные форматы:

- PNG для отдельных объектов.
- PNG + JSON для атласов анимации.
- Подходящие веб-форматы для фоновой музыки и звуков.

Игровые объекты должны иметь прозрачный фон.

Не использовать изображения с уже встроенными чужими элементами HUD.

## 13.2. Координаты и точки опоры

Для врагов:

- Опорная точка в районе ступней.
- Устойчивое положение между кадрами.
- Согласованный размер кадров анимации.

Для деревьев и лавочек:

- Опорная точка у основания объекта.
- Совместимость с перспективным масштабированием.

Для кулаков:

- Позиционирование в экранных координатах.
- Независимость от координат дорожки.
- Возможность анимировать каждую руку отдельно.

## 13.3. Анимации

Для каждого состояния врага использовать соответствующую анимацию.

Состояние анимации должно определяться игровым автоматом состояний, а не наоборот.

Запрещается определять факт попадания исключительно по визуальному пересечению спрайтов.

## 13.4. Временные ассеты

До готовности финальной графики допускаются:

- Простые силуэты.
- Цветовые обозначения типов врагов.
- Временные изображения кулаков.
- Простые геометрические объекты окружения.

При замене изображений на финальные не должна изменяться логика боя или проекции.

# 14. Внутреннее меню разработчика

## 14.1. Назначение

Меню необходимо для балансировки без изменения кода.

Доступ только в режиме разработки или через контролируемый скрытый способ открытия.

Не допускать случайного открытия в обычном игровом процессе.

## 14.2. Категории параметров

**Player**

Здоровье, выносливость, расход на удары, восстановление, тайминг блока.

**Combat**

Дистанция ударов, урон, ширина сектора поражения, длительность комбо, бонус контратаки.

**Enemies**

Здоровье, скорость, урон, время замаха, период между атаками, скорость перемещений.

**World**

Скорость движения, горизонт, глубина отрисовки, кривизна поворотов, плотность окружения.

**Level**

Выбор столкновения, запуск босса, управление контрольными точками, перезапуск.

**Visual / Debug**

FPS, зоны поражения, активные цели, состояние AI, координаты и дистанции.

## 14.3. Хранение настроек

Базовые значения хранятся в конфигурации игры.

Изменённые значения могут сохраняться локально.

Обязательна кнопка восстановления настроек по умолчанию.

Меню должно явно показывать, что текущая сессия запущена с изменёнными параметрами.

# 15. Адаптация под мобильные экраны

## 15.1. Ориентация

Поддерживается только портретный режим.

При горизонтальной ориентации показывается экран с предложением повернуть устройство.

Не полагаться исключительно на программную блокировку ориентации браузера.

## 15.2. Разрешение

Базовый ориентир — 360 пикселей по ширине при логической высоте около 640 пикселей.

Для более вытянутых смартфонов рекомендуется адаптивная логическая высота, а не растягивание всей сцены.

Варианты Phaser Scale Manager необходимо проверить на устройстве.

Рекомендуемый принцип:

- Сохранять пропорции объектов.
- Увеличивать доступную вертикальную область.
- Не обрезать важные элементы HUD.
- Не изменять игровую дистанцию атаки из-за изменения пропорций экрана.

## 15.3. Safe Area

Обязательно учитывать:

- Вырез камеры.
- Dynamic Island.
- Нижний индикатор жестов.
- Изменения размеров области браузера.

Верхние показатели и нижняя шкала выносливости должны находиться внутри безопасной зоны.

## 15.4. Пиксель-арт

Использовать отображение без сглаживания пикселей, где это применимо.

Избегать неуправляемого размытия спрайтов при масштабировании.

Разрешить небольшой субпиксельный расчёт положения для плавности движения, но итоговое отображение должно сохранять согласованный пиксельный стиль.

# 16. Игровой цикл и производительность

## 16.1. Обновление логики

Использовать стабильный шаг симуляции.

Рекомендуемый целевой шаг — 1/60 секунды.

Время игровой симуляции должно быть отделено от фактической частоты обновления экрана.

При задержках кадров ограничивать число догоняющих обновлений, чтобы избежать чрезмерного накопления вычислений.

## 16.2. Рендеринг

Целевой FPS — 60.

Начать с разумного числа одновременно видимых дорожных сегментов, например 40–80, и настроить количество по результатам профилирования.

Избегать:

- Постоянного создания и удаления большого количества объектов.
- Генерации новых текстур в каждом кадре.
- Многократного пересоздания анимаций.
- Избыточной сортировки неизменившихся объектов.
- Сложных эффектов на всех врагах одновременно.

При необходимости перейти от прямой отрисовки дорожных полигонов к оптимизированному специализированному рендереру.

## 16.3. Отладка

Предусмотреть отображение:

- Текущего FPS.
- Времени обновления симуляции.
- Количества видимых сегментов.
- Количества отображаемых спрайтов.
- Количества активных противников.
- Текущего игрового состояния.

# 17. Звук

Создать отдельную систему воспроизведения аудио.

Предусмотреть:

- Одновременные звуки ударов и реакции врагов.
- Ограничение повторов одинакового звука при быстрых тапах.
- Разные звуки попадания и промаха.
- Сигналы блока и контратаки.
- Фоновую музыку.
- Отключение звука.
- Корректную паузу аудио при сворачивании игры.

Учитывать требования мобильных браузеров: запуск аудио может потребовать первого пользовательского взаимодействия.

# 19. Порядок технической реализации

## Milestone 3 — Group Combat

Цель: проверить групповые столкновения.

Реализовать:

- Три типа врагов.

- Контроллер очередности атак.
- Урон по соседним противникам.
- Комбо.
- Очки.

## Milestone 4 — Level Flow

Цель: реализовать законченный уровень.

Реализовать:

- Возрождение.
- Мини-босса.
- Добивание.

**Критерий готовности:** уровень можно пройти от старта до финала, а после поражения продолжить с нужной точки.

## Milestone 5 — Art & Polish

Цель: заменить временную графику и улучшить игровой опыт.

Реализовать:

- Интеграцию финальных спрайтов.
- Полноценные анимации.
- HUD.
- Звуки.
- Визуальные эффекты.
- Меню разработчика.
- Оптимизацию.

**Критерий готовности:** стабильный играбельный прототип на целевых мобильных браузерах.

# 20. Тестирование

## 20.1. Проверка псевдо-3D

- Дорожка непрерывная, без разрывов сегментов.
- Повороты плавные.
- Объекты остаются привязанными к окружению.
- Объекты корректно увеличиваются при приближении.
- Порядок перекрытия правильный.
- Остановка героя не останавливает AI врагов.
- При возобновлении движения перспектива продолжает работать.

## 20.2. Проверка управления

- Короткий тап создаёт один удар.
- Удержание включает блок.
- Отпускание блока не создаёт удар.
- Мультитач не вызывает дублирование действий.
- Потеря фокуса не оставляет персонажа в бесконечном блоке.
- После возвращения в игру управление продолжает работать.

## 20.3. Проверка боя

- Выносливость расходуется корректно.
- Промахи обрабатываются по GDD.
- Третий удар получает повышенный урон.
- Соседние враги получают частичный урон.
- Контратака прерывает вражеское действие.
- Бонус контратаки применяется к нужной цели.
- Автонаведение не переключается хаотично.
- Во время группового боя соблюдается очередность атак.

## 20.4. Проверка прогресса

- Волны появляются по заданному сценарию.
- Контрольные точки активируются вовремя.
- После поражения применяются правильные штрафы.
- Нельзя повторно получать очки за уже награждённого врага.
- Перед боссом восстанавливается здоровье.
- После поражения от босса третий участок повторять не требуется.
- Итоговый ранг зависит только от очков.

## 20.5. Проверка мобильных устройств

В первую очередь:

- iPhone Safari.
- Android Chrome.

Проверить экраны с разной высотой, вырезами и безопасными областями.

Важны не только FPS, но и задержка ввода, корректность жестов и отсутствие чрезмерного нагрева устройства.

# 24. Definition of Done — технический прототип v1.0

Работа считается завершённой, когда:
